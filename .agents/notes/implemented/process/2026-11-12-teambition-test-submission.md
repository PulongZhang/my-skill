# Agent Note: Teambition 提测与工作流状态校验

Status: implemented

## Problem

用户明确要求在 TB 新建提测单并指派测试人员后，技能仍要求用户提供内部起始状态 ID；项目参考还混淆“测试单”和“测试任务”，从任务面板复制的项目内链接也可能跳回已关闭的任务分组。创建成功后界面未及时关闭时，重复点击可能产生重单；元数据响应还可能包含不应输出的临时签名链接。

## Decision

以 S1867 实际部署观察到的 SFC 状态元数据作为运行时证据，按目标项目、任务类型及实际工作流校验状态；用户已明确授权业务动作且结果唯一、符合操作语义时，无需用户提供内部 ID，异常或歧义时停止。其他部署只有实际响应满足同等校验时才可使用该发现方式。

独立提测单流程按明确授权创建并指派、填写有证据的版本与回归范围、转换到实际工作流的“已提测”中间状态，并独立回查。创建和状态转换分别处理未知结果，不盲目重试；交付优先使用已验证的同源 `/task/{id}` 链接。元数据输出采用必要字段白名单，不输出临时签名 URL、凭据或无关正文。

工时模板仍只支持 S1867 需求类型和 904 起始状态；需要创建任务时，在该次 F12 运行内重新校验列表、阶段、SFC 的归属及唯一有效起始状态。项目阶段接口当前返回 `isArchived=null` 时仅接受这一已观察形态，不把它解释为明确的未归档布尔值。

## Alternatives considered

继续由用户提供和确认每个起始状态 ID 可以维持原有人工门禁，但已验证的实时元数据能够直接证明类型、归属和 `kind`，重复询问增加操作负担。改为实时校验并对歧义停止，保留现有明确授权和写后回查。

使用固定项目内复制链接可以直接沿用 UI，但本次实际跳回已关闭的任务分组；使用经新标签验证的 `/task/{id}` 直达链接，并保留其他部署无法验证时的保守退路。

## Verification

- 2026-11-12 在已登录的 S1867 页面只读查询 SFC，核对“测试单”“测试任务”、需求状态及其工作流；本次文档中的只读示例分别取得测试单的起始、已提测和终态，返回内容仅包含白名单字段。
- `node --test teambition-task-api/tests/workflow-metadata.test.mjs` 的 5 项测试通过，覆盖正常状态、缺失或歧义、归属错误、重复 ID、未知状态、敏感字段过滤及工时模板的写前门禁；完整模板测试使用模拟请求，没有外部写入。
- 先前经用户授权的 1.2.162 测试单实际完成创建、指派和“待处理 → 已提测”，独立回查了状态和执行者；新标签验证 `/task/{id}` 可直接打开。此次技能维护没有再次创建、修改或提交线上任务。
- 技能元数据验证、26 个本地 Markdown 链接及锚点检查和 `node --check` 通过。

## Consequences

提测可复用真实项目配置并返回可用链接，避免用户反复提供内部 ID；代价是每次都要实时核验配置和写后状态。接口结构可能随部署升级改变，不能把历史 ID 当作默认值。`POST /api/tasks` 和状态转换无可证明的幂等键，未知结果必须先独立回查；其他部署与未验证的自定义字段写接口不能直接套用。
