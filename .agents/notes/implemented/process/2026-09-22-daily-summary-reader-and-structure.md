# Agent Note: 日报默认面向非技术领导并改用约 350 字逐段细节

Status: implemented

## Problem

`daily-work-summary` 原先默认把读者当成能读代码的同事：正文可以用总述开场，可以用“部署方面”“业务方面”这类标签分段，长度下限为 300 字，英文策略也只要求“有自然中文等价词时翻译”。实际使用时，成果要给领导或非技术一线同事阅读，常见问题不是事实不够，而是技术动作没有被翻译成人话，段落先讲分类再讲细节，关键信息被组件名、变量名和实现细节淹没。

## Decision

日报默认面向领导或非技术一线读者。读者可以理解接口、配置、日志、数据库、部署、服务注册等通用概念，但不默认理解具体组件名、实现细节或内部标识。

正文写入以下约束：

- 默认约 350 字，按用户当次要求调整，不再把 300 字当作固定下限。
- 不先写“今天的工作围绕……展开”一类总述，也不用“XX方面”作为段落标签。
- 每段直接描述一个具体工作事项，讲清问题、动作和所处环节；技术动作翻译成普通职场中文。
- 英文只保留必要的专有名词或没有自然中文名称的标识；通用技术概念优先使用中文。

`evals/evals.json` 增加一个面向领导、约 350 字、禁止总述和“XX方面”标签的样例，并把既有样例的预期输出同步到新读者模型。

## Alternatives considered

- **继续把“至少 300 字”当作唯一长度规则**：用户已经多次把输出压到 300 至 350 字附近，固定下限会诱导模型填充总述和重复信息。
- **只增加“少用英文”规则，不改读者模型**：问题根源是默认读者错误，技术动作是否要解释取决于读者是否理解实现细节，单独控制英文量无法覆盖。
- **完全禁止技术名词**：领导仍需要理解部署、注册、数据库、错误返回等共同语境；一律去技术化会丢失事项定位信息。
- **保留“XX方面”作为段落标签**：标签会先给出分类，正文再补细节，读起来像模板报告，无法直接讲具体事项。

## Consequences

- **收益**：默认输出更接近领导能直接阅读的日报；每段承载一个事实，减少总述和分类标签带来的空话；长度规则更贴近真实使用习惯。
- **代价与上限**：深入浅出依赖写作者对事实的理解，不能靠机械替换术语完成；部分包含跨系统链路的日报需要更详细的前提解释，可能需要超过 350 字。
- **对既有行为的影响**：用户明确要求“详细”时仍可扩展长度；原有证据边界、来源隐藏、禁用人称代词和禁用“了”等规则不变。

## Verification

- 检查 `SKILL.md`：默认读者、约 350 字、逐段细节、禁止总述和“XX方面”标签、英文限制均写入正文规则与回答前检查表。
- 检查 `evals/evals.json`：既有样例预期输出同步到新读者模型，并新增领导阅读与段落结构样例。
- `uv run --project daily-work-summary python -m unittest discover -s tests`：确认提取脚本测试不受文档规则修改影响。
