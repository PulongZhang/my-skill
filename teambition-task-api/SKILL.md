# Teambition 任务 API

## 概览

在 Chrome DevTools 已连接且 Teambition 页面已登录时，优先直接执行同源请求；否则生成供用户手动运行的 F12 控制台脚本。开始浏览器操作前先读取目标项目参考并解析实际部署 origin；内网部署不得猜成公有云 `www.teambition.com`。例如 S1867 必须先读 [`references/s1867.md`](references/s1867.md)，再使用其中记录的内网地址。

所有写操作必须遵循同一顺序：

**查询现状 → 明确计划 → 用户授权 → 写前校验 → 修改 → 独立验证**

查询可直接执行。创建任务、登记工时、删除记录和修改任务状态均属于外部写操作，必须先取得用户明确授权。

### 已验证范围与边界

| 场景 | 当前支持情况 |
|---|---|
| 查询组织内某执行者的全部未完成任务 | 支持；必须完成 GraphQL 全分页，再按项目本地过滤 |
| 查询项目、任务列表、阶段、SFC 等元数据 | 支持只读查询；不修改项目元数据 |
| 补录工时 | 支持；先形成逐日计划，确认后运行时重查并仅补缺口 |
| 为工时计划创建缺失任务 | 支持；只能使用已验证的 SFC 起始状态，创建后独立核验 |
| 单独批量创建任务 | 可复用“补录工时”的任务识别、元数据校验与创建后验证规则，但必须形成独立计划和授权，不得顺带登记工时 |
| 完成工作流任务 | 支持；只能使用任务实际 SFC 已验证的 `kind: end` 状态 |
| 检查工时涉及任务的状态 | 支持；直接按工时记录中的任务 ID 查询，不与未完成任务集合取交集 |
| 通用任务字段编辑、项目元数据修改 | 当前没有已验证流程，不应凭经验调用 |
| 删除任务或工时 | 仅保留为需单独核实的高风险场景；接口响应和写后查询契约未确认前不得执行 |

当前 `work-time-fill-template.js` 是兜底实现：每个日期仅支持一个工作切片，且要求当前登录用户、工时所属用户和任务执行者相同。一天存在多个任务、同一任务下存在多个工作切片，或工时参与者不是任务执行者时，应先生成显式分配方案和针对该方案的脚本，不要直接套用模板。

## 执行决策

1. 先从用户提供的 URL、当前页面和项目参考中解析部署 origin。项目参考已经记录地址时必须读取并复用，不得先打开同名公有云站点试探。
2. 用户明确要求 MCP Chrome / Chrome DevTools 时，把该浏览器表面视为硬约束：先发现并调用 `mcp__chrome_devtools__list_pages`（有些环境显示为 `mcp__chrome-devtools__list_pages`），不得用内置浏览器或其他浏览器代替。不要仅因初始可见工具列表中没有它就断言不可用，应先完成工具发现。
3. 调用 `list_pages` 查找已打开的 Teambition 页面。找到后先用 `select_page` 选中；没有时只在空白页导航到已确认的部署 origin，或用 `new_page` 新开页面，避免覆盖无关标签页。
4. MCP Chrome、内置浏览器和用户日常浏览器可能使用不同会话。导航后必须重新检查实际 URL 和登录态，不能用另一个浏览器已登录来推断当前 MCP Chrome 已登录。
5. `navigate_page` 只用于已选中的 Teambition 页面或空白页，以打开或刷新已确认的目标 URL。
6. 选中目标页面后检查 URL。如果包含 `/login`，立即停止并要求用户完成登录；登录前不得请求业务接口。
7. 已登录时，使用 `evaluate_script` 在页面内执行同源 `fetch`：
   - 查询操作可直接执行；
   - 创建、登记工时、删除、修改状态前必须展示具体计划并取得明确授权；
   - 每次脚本应自包含配置、请求 helper、操作逻辑和返回结果，不依赖上次执行留下的全局变量。
8. Chrome DevTools 不可用，或用户要求手动运行时，生成完整、自包含的 F12 IIFE：`(async () => { ... })();`：
   - 只读请求的 IIFE 只包含查询、完整性检查和结果报告，不得包含任何写接口；
   - 写请求的 IIFE 必须执行“运行时查询 → 校验 → 预览 → `window.confirm`（明确允许取消）→ 写入 → 独立验证”，用户取消时不得产生写入。
9. 始终让浏览器复用同源登录态。不得读取、打印或手工拼接 `Cookie` / `Authorization`。

接口路径、请求字段和可复用函数见 [`references/api.md`](references/api.md)。

## 标准流程 A：查询全部未完成任务

1. GraphQL 使用以下 TQL，按执行者查询组织内未完成任务：

   ```text
   isArchived = false AND isDone = false AND executorId = "用户ID"
   ```

2. 遍历所有分页：读取 `pageInfo.hasNextPage` 和 `pageInfo.endCursor`，将上一页 `endCursor` 作为下一页游标，直到 `hasNextPage=false`。
3. 如果 `hasNextPage=true` 但 `endCursor` 为空，立即报错并说明结果不完整，不得把已取得页面当作全量结果。
4. `project` 不是合法 TQL 字段。必须先完成组织级全分页，再按 GraphQL 节点的 `node.project.id`（整理后的结果字段为 `project.id`）在本地过滤项目。
5. 返回前再次排除 `isDeleted=true`、`isArchived=true` 或 `isDone=true` 的任务。
6. 报告查询范围、执行者、分页是否完整、项目过滤条件和最终任务数量。

不要改用未经验证的项目查询参数代替组织级全分页。

## 标准流程 B：补录工时

补录工时必须严格分为两个阶段。只读阶段结束后必须等待用户确认，不能在同一轮自动进入写入。

### 阶段 1：只读分析与计划

1. 查询目标日期范围内该用户每天已有的工时和工时记录。日期聚合必须包含归档任务，`filter.task` 使用空对象 `{}`，不得使用 `isArchived=false`，否则可能漏算并重复补录。解读每日 `workTime` 时必须把毫秒换算成小时（`1440000 ms = 24 分钟 = 0.4 小时`，不是 4 小时；换算公式：`小时 = ms / 3600000`），并以此为准计算缺口，不得凭 ms 数值大小粗略估计小时数。
2. 查询现有任务并识别可复用项：已有准确任务 ID 时必须用 `tasks/bulk` 精确校验；没有准确 ID 时必须复用流程 A 的组织级全分页，再按 `project.id` 本地过滤。分页不完整时停止，禁止建议或执行创建。
3. 按任务 ID、准确标题、项目、SFC / 任务类型和实际工作内容识别精准唯一匹配。同名但 SFC 不同或候选不唯一时停止消歧，不得静默创建；已有工时不得覆盖或重复登记。用户明确指定的任务若不在“本人未完成任务”集合中，不得直接判定不存在：它可能由其他人执行、已经完成或归档。应按准确 ID、项目任务列表或该任务实际执行者扩大只读查询并校验；不能用当前部署中不可靠的 `content = "标题"` TQL 代替精确核对。
4. 输出计划，逐项列出：
   - 复用哪个现有任务及其 ID；
   - 哪些工作没有可复用任务，建议新增什么任务及类型；
   - 每天已有时长、目标时长、缺口，以及每个拟登记工作切片的任务、时长和说明；
   - 哪些匹配不唯一或信息不足，需用户决定。
5. 计划的最小单位是“可由事实单独说明的工作切片”，不是“日期”。同一天存在多个独立产出时应拆成多条；即使挂在同一任务下，也应分别保留不同说明。反过来，不要为了增加条数把连续工作硬拆成近义句：每条必须对应不同问题、产出或处理阶段，语义重叠的说明应合并或改写。展示前逐日检查近义重复、范围包含和同一成果的换词复述。
6. Git 提交时间或深夜会话只能证明活动线索，不能单独推断标准工时、周末工时或加班时长。目标时长属于计划输入；若采用“工作日 8 小时”等口径，必须在计划中显式说明并让用户确认。
7. 等待用户明确确认计划以及其中的创建任务、登记工时等写操作。用户对计划的修改只改变明确提到的日期、任务、切片或说明；执行前应复述最终纳入和排除范围，例如“某日不写”。

### 阶段 2：运行时重查与执行

1. 获得授权后重新查询日期聚合和候选任务，不能直接使用阶段 1 的旧结果写入。日期聚合仍使用 `filter.task: {}`；准确 ID 必须再次用 `tasks/bulk` 校验，标题候选仍复用流程 A 的组织级全分页并按 `project.id` 本地过滤，分页不完整禁止创建。
2. 对复用任务逐项校验 ID、标题、项目、SFC、执行者、删除/归档/完成状态；SFC 必须纳入授权方案，变化时停止。归档状态 `tasks/bulk` 不返回，必须用 GraphQL 的 `isArchived` 校验。发工时前再对所有最终任务 ID 做一次 bulk 预检，异常项不得写入。任务执行者与工时所属用户不同时，只有用户已明确把自己的参与工时映射到该精确任务，且任务身份和实际执行者均已展示并确认，才可生成自定义脚本；不得改执行者、完成任务或套用本人补录模板。
3. 仅在没有精准唯一匹配、不是重名歧义，且运行时仍有工时缺口时创建任务。创建前在循环外一次性查询并校验任务列表、阶段和 SFC 元数据；阶段接口不得用于猜工作流状态。当前仅验证了 S1867 需求 SFC 的起始态 `904`；其他 SFC 必须停止，直到用户提供并确认属于实际 SFC 工作流且 `kind: start` 的状态配置。
4. 发 batch 前再做一次靠近写入的全日期聚合重查：缺口增加时停止，减少时只补更小缺口，已满时跳过。已有记录应先按任务、日期、时长和说明匹配已授权切片，避免重复补同一工作。若缺口缩小但无法判断哪条切片已存在，不得机械截断或挪用其他说明，应输出修订计划重新确认。batch 响应和写后聚合都必须按本次记录 ID、任务、日期、时长及记录数逐项核对；每日总量严格等于目标才成功，超过目标须报告超额/并发冲突。
5. 运行时重查只能自动减少或跳过已授权操作。若结果要求增加工时、增加日期、新建任务、改变任务 ID/标题/类型、改变目标状态或扩大任何写入范围，必须输出修订计划并重新取得明确授权。
6. 按任务汇总 batch 请求，同时保留工作切片顺序和逐日缺口边界。`times` 可以包含多天，也可以为同一任务、同一日期包含多条不同说明；不得用 `Map(date -> time)`、日期去重或“每天一条”的校验吞掉切片。响应必须按输入项逐条核对并保存每个记录 ID。
7. 写入后重新调用日期聚合，按日期独立核对总工时、记录数和新增记录；不能只检查登记接口返回值。
8. 逐项报告已创建任务、已登记工时、跳过项、失败项和验证结果。

复用任务或新建任务都不得默认标记完成。任务名和工时描述必须反映实际工作；方案、Demo、评审不得误写成正式开发。

用户从 Git 提交或日报发起补录时，先用 `daily-work-summary` 提取并客观归纳实际工作，再把结果作为候选计划交给本 skill。`daily-work-summary` 默认同时覆盖 Git 提交记录和本地 Claude 会话记录，二者都会作为日报的事实素材。交接内容至少包含日期、实际工作说明、候选任务 ID/标题、项目/SFC 和拟登记时长；提交记录和会话记录都不能直接视为 Teambition 写入授权，也不能仅凭记录信息夸大工作性质。

F12 工时模板见 [`work-time-fill-template.js`](work-time-fill-template.js)。执行前必须把组织、当前登录用户、工时所属用户、任务执行者、项目、SFC、目标时长和工作计划视为本次运行输入逐项核验；不得把模板中的历史示例值当作默认值。模板仅适用于“当前登录用户 = 工时所属用户 = 任务执行者”的本人补录场景，且每个日期只能有一个任务；不满足时应生成符合已确认方案的新脚本。模板内容必须符合主流程，不得绕过授权和校验。

## 标准流程 C：批量完成任务

1. 用户必须明确指定要完成的任务，优先使用任务 ID；仅给出模糊标题时先查询并消歧，不能直接写入。
2. 生成计划前按首次出现顺序稳定去重任务 ID；调用 bulk 前和发出 PUT 前都只使用该去重结果。重复输入只执行一次，并在报告中列明已合并的重复 ID。
3. 写前调用 `POST /work-time-server/api/tasks/bulk`，逐项核对：
   - 请求 ID 与返回任务 ID；
   - 名称与用户指定目标；
   - 项目；
   - SFC / `_scenariofieldconfigId`；
   - `isDeleted`、`isDone`（`tasks/bulk` 不返回归档状态，`isArchived` 恒为 `null`，归档校验必须用 GraphQL）；
   - 当前 `isDone` 和 `_taskflowstatusId`。
4. 逐项确认目标状态 ID 属于任务实际 SFC 对应的工作流且 `kind: end`。当前仅验证了 S1867 需求 SFC 的终态 `907`；其他 SFC 必须停止，直到用户提供并确认属于实际 SFC 工作流且 `kind: end` 的状态配置，不得自动猜测，也不得复用需求终态。
5. 数量不符、ID 缺失、重名、项目不符、类型不符、已删除或已归档时停止对应项，并向用户报告。归档状态以 GraphQL 查询为准（`tasks/bulk` 不返回）。根据当前状态继续判断：
   - `isDone=true` 且状态正是目标终态：跳过并报告；
   - `isDone=true` 但处于其他终态：停止，请用户决定；
   - `isDone=false` 但状态 ID 已是目标终态：视为数据异常并停止。
6. 工作流项目只使用 `PUT /api/tasks/{id}/taskflowstatus` 修改状态。
7. 默认启用必填校验。只有用户明确授权跳过目标状态必填字段时，才可使用 `sfcRequiredValidateEnable: false`。
8. 发出 PUT 前再次稳定去重任务 ID；写后调用 `tasks/bulk`，逐项要求：
   - 返回了目标任务；
   - `isDone=true`；
   - `_taskflowstatusId` 等于目标终态 ID。
9. 不得使用 `PUT /api/tasks/{id}` 携带状态字段，也不得使用 `PUT /api/tasks/{id}/isDone` 完成工作流任务。

更新接口返回 HTTP 200/204 只说明请求被接收，不代表业务状态已经正确变更。

## 标准流程 D：检查工时涉及任务的状态

1. 查询目标日期范围的工时聚合。为避免漏报归档任务，`filter.task` 必须使用空对象 `{}`，不得使用 `isArchived=false`。
2. 仅从 `payload[].objects` 中提取 `objectType=task` 的 `_objectId`。
3. 对任务 ID 去重后，直接调用 `POST /work-time-server/api/tasks/bulk` 查询详情并按请求 ID 对账。
4. 不得与“当前未完成任务”集合取交集；有工时的任务可能已经完成、归档或删除。
5. 按以下互斥顺序分类，命中前一类后不得进入后续类别：
   1. 未知/缺失（bulk 未返回对应 ID）；
   2. 已删除；
   3. 已归档；
   4. 已完成；
   5. 未完成。

未知/缺失不能推断为未完成、删除或处理成功。`tasks/bulk` 不返回 `isArchived`（恒为 `null`），要把“已归档”作为独立分类必须另行用 GraphQL 查询归档字段，不能从 bulk 结果推断未归档。

## 安全约束与失败处理

- 查询可直接执行；所有外部写操作必须获得用户明确授权。
- 不按模糊标题直接写入。标题重名、任务数量不符、项目或任务类型不一致时停止并请求消歧。
- 不把参与者登记工时等同于任务执行者，不代替他人完成任务。本人可以在用户明确指定且精确验证的他人执行任务下登记本人的参与工时，但必须展示执行者差异，使用自定义脚本，并保持任务执行者和状态不变。
- 不默认完成复用任务或新建任务；登记工时与完成任务是两个独立授权动作。
- 写接口 HTTP 200/204 不等于业务验证完成；必须通过独立查询检查最终状态。
- 批量操作部分失败后，逐项报告成功、失败和未知结果，并重新查询现状；只重试明确失败且仍需处理的项，不盲目整体重跑。
- 创建任务和登记工时接口没有幂等键。运行时查询、准确任务 ID 和每日缺口计算只能降低重复风险，不能承诺并发下绝对唯一。
- 删除不可恢复。当前资料尚未确认任务删除响应和两类删除的完整写后查询契约，因此不得仅凭已记录的 endpoint 执行删除；应先通过只读方式确认请求/响应与独立验证方法，再向用户展示具体任务 ID 或工时记录 ID 并取得单独授权。
- 不因脚本曾执行失败就假设没有产生写入；重试前先重新查询。
- 认证失效、响应结构不符、分页不完整或 bulk 对账缺失时停止，不带着不确定状态继续写入。
